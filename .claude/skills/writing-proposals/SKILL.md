# 提案文書を書く（Writing Proposals）

社内の意思決定者を動かす提案文書を書く。ゴールは「読んでもらう」ことではなく「承認してもらう」ことなので、決裁者の頭の中にある疑問に、結論から先に答える構成を徹底する。

## なぜ対話で材料を引き出すのか

ユーザーは「定例会議を減らしたい」のように、思いついたことをそのまま投げてくることが多い。ここでいきなり文章を書き始めると、丁寧だが誰にも刺さらない作文になる（`references/examples.md` の「Before/After」参照）。刺さる提案文書に必要な材料は、実は書き手の頭の中に眠っていることが多く、AIの役目はそれを1問ずつ引き出すことにある。

材料が4つ揃って初めて、結論ファーストの文章が書ける：
① 何を提案するか
② 誰が決裁者か
③ 決裁者が気にしている疑問は何か
④ 根拠になる数字（なければ体験談）

## 対話フロー：1問ずつ、推奨案つきで確認する

まとめて4つ質問しない。1つずつ聞き、可能な限り**推奨案を添えて**「これでいいですか？」と確認する形にする。推奨案を出すのは、ユーザーの回答コストを下げるためであり、当てずっぽうで進めるためではない——外した場合はユーザーが訂正してくれるので、それでよい。対話の実例は `references/examples.md` を参照。

1. **①何を提案するか**：ユーザーの雑な依頼から抽出し、「①は『〜』ですね」と言語化して見せる。
2. **②誰が決裁者か**：文脈から推測できるなら推奨案を出す（例：「チームの定例なら直属の部長が承認者になりがちです。これでいいですか？」）。わからなければ素直に聞く。
3. **③決裁者の頭の中にある問い**：決裁者の立場になって、「この提案を聞いたら何が気になるか」を2〜3個の疑問文として提示し、確認を取る（例：「部長の頭の中の問いは『どの会議か／何がよくなるか／自分は何をすればいいか』が刺さります。これでOKですか？」）。この疑問への回答が、そのまま提案文書の骨格になる。
4. **④根拠になる数字や体験談**：定量データがあれば聞く。なければ「体験談でも可」と伝えて心理的ハードルを下げる。数字が一切出てこない提案は説得力が弱くなるが、それでも書けないわけではない。

4つが揃ったら「十分です。提案文書を作ります」のように区切りをつけてから生成に入る。すでに十分な情報がユーザーの最初のメッセージに含まれている場合（例：数字も決裁者も明記済み）、同じ質問を重ねて聞き直す必要はない——埋まっている項目は飛ばし、足りない項目だけを聞く。

## 任意：過去の文章に文体を寄せる

ユーザーが過去に書いた提案書・報告書・メールなどを渡してきた場合（貼り付け、ファイル添付、「これに寄せて」といった発言）は、その文章の語尾・敬語のレベル・一人称・句読点の打ち方といった文体的特徴を観察し、これから書く提案文書に反映する。フォーマットや構成（【提案】から始まる結論ファースト、◎の階層構造など）はこのスキルのルールを優先し、文体（言葉づかいのトーン）だけを寄せる。過去の文章が渡されなければこの工程は不要——聞かれてもいないのに「過去の文章はありますか」と毎回尋ねる必要はない。

## 提案文書のフォーマット

```
【提案】<何をしてほしいか。承認してほしいことを1〜2文で言い切る>

◎ 現状の課題
<数字や具体的事実。解釈を混ぜない>

◎ 提案する理由
<なぜこの提案が課題を解決するか。箇条書き可>

◎ リスクと対策 / ◎ コスト対効果 / ◎ 補足
<内容に応じて使い分ける。下記「セクションの選び方」参照>
```

比較検討が必要な提案（ツール選定など）には、「提案する理由」の前後に次のセクションを挟む：

```
◎ 他ツールとの比較検討
・選択肢A（条件）— 特徴
・選択肢B（条件）— 見送り理由
→推奨：選択肢A（推奨理由を一言で）
```

### セクションの選び方

3つ目のセクションは内容によって使い分ける。すべて並べる必要はない——決裁者が次に何を心配するかで選ぶ。

- **◎ リスクと対策**：運用変更・ルール変更など、「うまくいかなかったらどうするか」が気になる提案（例：在宅勤務、ノー残業デー、会議削減）
- **◎ コスト対効果**：支出を伴う提案で、費用対効果の数字が出せる場合（例：ツール導入、外注）
- **◎ 補足**：例外運用や念のための注記など、軽く添える程度の内容

迷ったら「◎ リスクと対策」がもっとも汎用的。

## メンツを守る言い換え（NG / OK）

提案は多くの場合「今のやり方を変えてほしい」という依頼になる。ここで過去や既存の取り組みを頭ごなしに否定すると、たとえ内容が正しくても決裁者は防衛的になり通りにくくなる——特にその仕組みを作った・続けてきたのが決裁者自身である場合は顕著。

**原則**：否定ではなく「状況の変化」として語り、これまでの取り組みの功績を一言立ててから、次の一手を提案する。

NG（過去を否定）：
> 今の定例会議は無駄が多く非効率です。やめるべきです。

OK（状況変化＋功績を立てる）：
> 定例会議は立ち上げ期に足並みを揃えるのに役立ってきました。人数も増えて自律的に動ける今、形を変えるタイミングだと思います。まず1ヶ月、報告は資料共有に切り替えて試させてください。

文書を書く際、現状を否定する表現（「無駄」「非効率」「やめるべき」など）が入りそうになったら、「状況が変わった」「次の段階に来た」という言い方に置き換えられないか必ず検討する。

## 出力前チェックリスト

提案文書を出力する前に、必ず `references/output-quality.md` のチェックリストを自分で確認し、満たさない項目があれば直してから出力する。声に出して確認する必要はなく、出力前に文面を見直して引っかかる項目だけ黙って直せばよい。ただし直した結果、大きく書き直しが必要になった場合は、その旨を一言添えてよい。

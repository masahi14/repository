## 最重要の安全制約(絶対に忘れてはいけない)

**本ツールが自動入力してよいのは、臨床的な事実に基づいてスタッフが選ぶ処置コード・定型文言・メニュー選択のみ。測定値・時刻など事実を表す数値は絶対に自動生成しない。** これは今後も新しい要望が来るたびに必ず確認すること。コード上も `src/lib/InputEngine.ahk` の `_HandleLeaveBlankManualEntry()` や `config/sets.schema.json` のフィールド制限で多層的に担保している(詳細は `docs/architecture.md`)。方法2(メニュー選択)も、あらかじめ決められた固定のキー操作を再生するだけで、画面を読み取って動的に判断したり数値を入力したりすることは一切ない。

## 方法2(メニュー選択)の操作手順まとめ(実機検証済み)

- **`Shift+F4` → `F5`** で「カスタムコメント選択」(50以上のグループが並ぶ一覧)が開く。
- 複数選択(マルチセレクト)対応。各行の左の数字/アルファベット(1〜9, A〜G)を押すと選択状態になる(カーソル移動とは独立)。**見えている行のキーを押すだけでよく、下矢印で移動してから押す必要はない。**
- 選択後 **Enter** で最初に選択したグループのサブメニューが開く。サブメニュー内でも同様に複数選択→Enterで、次に選択したグループのサブメニューへ連鎖する。最後のサブメニューでEnterを押すと画面が閉じてカルテに反映される。
- **下矢印キーの回数計算**: カーソルは最初1番上。最初のページ(13行 or 16行タイプで異なる)の中はスクロールしない。ページを超えると、常にカーソルは表示ウィンドウの一番下に来る。よって絶対位置Nを選ぶには「下矢印を(N-1)回押し、その時点で一番下に表示されているキーを押す」。スクロール後の状態でも、その時点のウィンドウ内に見えている他の行は(下矢印を追加せず)同時に選択できる。
- 5桁コードが実は「候補メニューを開くトリガー」であるケースに注意(例: `denture`の`40177`)。
- 同じ内容が複数グループに重複して存在することがあるため、可能な限り実際の資料(パンフレット等)と照合するのが確実。

### 【最重要】このセッションで見つかった4つのコードバグ(すべて修正済み・コミット済み)

実機で動かして初めて判明した、`sets.json`の中身とは無関係のプログラム自体のバグ。**今後コードを変更する際、同じ実機(またはこれに似たAutoHotkey v2環境)で同様の問題が再発しうるので、必ずこのセクションを読んでから着手すること。**

1. **`ConfigLoader.ahk`**: `validatorFn`という関数参照を変数に入れて後で`.Call(data)`または`validatorFn(data)`のように間接的に呼び出す書き方が「Missing a required parameter.」エラーになった。**修正**: 関数参照を渡すのをやめ、`"sets"`/`"settings"`という種別文字列を渡して`_Validate(kind, data)`内で直接`ConfigLoader._ValidateSets(data)`のように呼び出す方式に変更。
2. **`Panel.ahk`**: `SetTimer(Panel._TrackActiveWindow, 200)` や `OnMessage(0x201, Panel._OnLButtonDown)` のように、静的メソッドを裸の値としてコールバックに直接渡す書き方が「Invalid callback function.」エラーになった。**修正**: `(*) => Panel._TrackActiveWindow()` のようにクロージャで包んで、通常の(丸括弧を使う)メソッド呼び出しの形にした。
3. **`tests/manual-test-harness/dummy-karte.ahk`**: 変数名 `edit` が AutoHotkey v2 の組み込み関数 `Edit()` と(大文字小文字を区別しないため)衝突し、「This Func cannot be used as an output variable.」エラーになった。**修正**: 変数名を `editBox` にリネーム。
4. **【最も重要】`InputEngine.ahk` のキー送信方式**: 当初の実装は `SendInput`(システム全体の「今フォーカスがある場所」に送る)+ `WinActivate` でカルテウィンドウを再アクティブ化する方式だった。しかし実機でtest_mode:falseにして初めて送信したところ、**エラーは出ないがキーがどこにも届かない**という現象が発生した。原因は、パネルがWS_EX_NOACTIVATEウィンドウであり、ボタン押下時に`WinActivate`でカルテウィンドウを最前面に戻そうとしても、Windowsがバックグラウンドプロセスによるフォアグラウンド奪取(SetForegroundWindow)を拒否することがあり、その場合SendInputはどこにも届かない(エラーにもならない)ため。**修正**: `ControlGetFocus("ahk_id " hwnd)` で対象ウィンドウ内の現在フォーカス中のコントロールを明示的に取得し、`ControlSend(keys, control, "ahk_id " hwnd)` で直接そのコントロールに送るように変更(`src/lib/InputEngine.ahk`の`_Send()`)。この方式は対象ウィンドウがフォアグラウンドである必要がないため、上記の制限を受けない。**この変更に伴い、ダミーカルテ側もReadOnly+グローバルHotkeyによる疑似実装をやめ、普通の編集可能なEditコントロールに変更した**(ControlSendはウィンドウメッセージを直接送るため、ReadOnlyコントロールやグローバルフックでは検知できないため)。

**教訓1**: この環境(実際に使われているAutoHotkey v2.0.26)では、静的メソッドやコールバックを「裸の関数参照」として変数や引数に渡す書き方全般が信用できない可能性がある。`(*) => ClassName.Method(args)` のようなクロージャで包む、または種別文字列で分岐して直接呼び出す、のどちらかのパターンに統一すること。

**教訓2**: 他プロセスのウィンドウにキーを送る際は、`SendInput`+`WinActivate`のような「フォーカスを奪ってから送る」方式ではなく、`ControlGetFocus`+`ControlSend`のような「フォーカスを奪わずに直接送る」方式の方が確実。実際のカルテソフトに対しても、この`ControlGetFocus`+`ControlSend`方式がそのまま使われる想定(現在の`InputEngine.ahk`はこの方式で実装済み)。もし実機カルテソフトで同様に入力が届かない場合、まずこのメカニズムを疑うこと。
